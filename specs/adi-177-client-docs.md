# ADI-177: target MCP client OAuth reference

Checked 2026-09-28 with real Codex CLI `0.155.1` and Claude Code `2.1.280` processes against a temporary local OAuth/MCP probe. The probe auto-approved authorization requests and rotated refresh tokens; it held no wallet, user, or budget data. Public metadata and the existing hosted OAuth lab were checked separately. No LanaTools OAuth server exists yet.

## Observed client behavior

| Step | Codex CLI 0.155.1 | Claude Code 2.1.280 |
| --- | --- | --- |
| Discovery | Requested unauthenticated `/mcp`, then `/.well-known/oauth-protected-resource` and `/.well-known/oauth-authorization-server`. | Requested `/.well-known/oauth-protected-resource/mcp` and `/.well-known/oauth-authorization-server`. The probe served both protected-resource paths. |
| Registration without CIMD | POSTed `/register` with claimed name `Codex`, `authorization_code` and `refresh_token` grants, and `token_endpoint_auth_method: none`. A second explicit `codex mcp login` registered a **new** client ID. | POSTed `/register` with claimed name `Claude Code (adi177-probe)`, the same two grants, and `none`. A second explicit `claude mcp login` reused its client ID and callback port; no second registration occurred. |
| Registration with CIMD advertised | Skipped `/register` and used `https://chatgpt.com/oauth/codex/client.json` as `client_id`. The [public document](https://chatgpt.com/oauth/codex/client.json) returned JSON and lists loopback callbacks. | Skipped `/register` and used `https://claude.ai/oauth/claude-code-client-metadata` as `client_id`. The public document returned HTTP 200 JSON and lists both `localhost` and `127.0.0.1` loopback callbacks. |
| Redirect and PKCE | Used `http://127.0.0.1:<ephemeral-port>/callback`; sent `S256`, `state`, `resource`, and requested `mcp:tools`. The token endpoint verified its code verifier. | Used `http://localhost:<ephemeral-port>/callback`; sent `S256`, `state`, and `resource`, but no scope when none was configured. The token endpoint verified its code verifier. |
| Refresh and reconnect | A fresh `codex exec` process refreshed a rotated token and sent authenticated MCP POST requests. Its model request then failed with API HTTP 401, so no model-directed tool call or result was verified. | A fresh `claude mcp get` process refreshed a rotated token, made authenticated MCP requests, and reported `Connected`. The probe's five-second access-token lifetime caused multiple successful refreshes during one connection. |

The local probe accepted either metadata route, issued five-second access tokens, consumed authorization codes once, verified S256 PKCE, and invalidated each refresh token on use. Only request shape and success status were recorded; no codes, verifiers, access tokens, refresh tokens, or wallet material belong in this note. The existing [hosted OAuth lab](https://pratik-mcp-oauth-lab.shambho.workers.dev/mcp) separately passed its discovery script: missing and invalid tokens returned 401, the resource and issuer matched its HTTPS origin, S256 was advertised, and `/register` was present. Browser SIWS, client token exchange against that hosted lab, and paid tools were not run.

## Requirements for ADI-181

1. Serve the protected-resource document at both the root well-known path and the `/mcp` path, and advertise the canonical HTTPS resource and authorization-server issuer. Preserve `resource` through authorization and token exchange.
2. Support CIMD for these clients and validate the fetched document, allowed loopback redirect host/path/port rules, and exact redirect URI used in each authorization code. Keep DCR for clients that need it. Both tested clients selected CIMD when offered; both used DCR when it was absent.
3. Require S256 PKCE, issue refresh tokens to public clients, rotate them, and allow a fresh client process to resume with its stored credentials. Use a practical access-token lifetime; five seconds made Claude refresh repeatedly.
4. Treat `client_name` and the MCP server alias as display text. A CIMD client ID identifies software, not one installation or connection. Store the grant and cumulative budget under the authenticated user, wallet, and server-issued grant identity bound to the OAuth client identity. A newly registered DCR ID must get new consent and a new limit, even if its claimed name matches an old connection. Reauthorization of the **same** grant must preserve spend. Never merge DCR registrations by name to make reconnect appear seamless.

This run establishes client compatibility requirements, not the LanaTools end-to-end release gate. Repeat both clients against ADI-181's actual HTTPS endpoint, including consent, token use, refresh, reconnect, revocation, and independent budget attribution before release.

## Primary-source reference

| Behavior | Codex CLI 0.155.1 | Claude Code 2.1.280 |
| --- | --- | --- |
| Start and discovery | `codex mcp add <name> --url <url>`, then `codex mcp login <name>`. The pinned login source resolves authorization metadata before selecting a client. [Codex guide](https://developers.openai.com/codex/mcp), [0.155.1 source](https://github.com/openai/codex/blob/rust-v0.155.1/codex-rs/rmcp-client/src/oauth_client_registration.rs) | Add an HTTP server, then authenticate via `/mcp` or `claude mcp login <name>`. A `401` or `403` signals sign-in; the docs say discovery checks protected-resource metadata first, then authorization-server metadata. [Claude MCP guide](https://code.claude.com/docs/en/mcp) |
| Client identity | `auto` chooses CIMD only if metadata advertises `client_id_metadata_document_supported: true`, `token_endpoint_auth_methods_supported` includes `none`, and the loopback callback is supported; otherwise it offers DCR. `--oauth-client-registration cimd\|dcr` selects a method for one login. A configured `--oauth-client-id` skips registration. [Codex guide](https://developers.openai.com/codex/mcp), [0.155.1 source](https://github.com/openai/codex/blob/rust-v0.155.1/codex-rs/rmcp-client/src/oauth_client_registration.rs) | Docs describe automatic CIMD discovery and DCR, with `--client-id` (and optional prompted `--client-secret`) for a pre-registered client if automatic setup fails. The public docs do not state CIMD versus DCR priority for this exact version. [Claude MCP guide](https://code.claude.com/docs/en/mcp) |
| Redirect and code flow | Default loopback callback is `http://127.0.0.1/callback`, with a chosen listener port inserted at login. A server-specific `/callback/<id>` is used without advertised issuer identification; issuer-bound callbacks can share `/callback`. The client validates a returned `iss` before code exchange. A configured callback and port must match what the provider accepts. [Codex guide](https://developers.openai.com/codex/mcp), [0.155.1 callback source](https://github.com/openai/codex/blob/rust-v0.155.1/codex-rs/rmcp-client/src/oauth_callback.rs) | Default callback uses a random port at `http://localhost:<port>/callback`; `--callback-port` fixes it, including with DCR. Docs state v2.1.231 restored `localhost` after a brief `127.0.0.1` regression. If browser redirect fails, the user can paste the full callback URL. [Claude MCP guide](https://code.claude.com/docs/en/mcp) |
| Refresh and reconnect | Pinned source stores token response, expiry, client ID, and issuer; it attempts serialized refresh near expiry, persists the new credentials, and requires authorization after a rejected refresh token. This establishes intended code behavior, not success with our server. [0.155.1 token source](https://github.com/openai/codex/blob/rust-v0.155.1/codex-rs/rmcp-client/src/oauth.rs), [refresh source](https://github.com/openai/codex/blob/rust-v0.155.1/codex-rs/rmcp-client/src/oauth/refresh_transaction.rs) | Docs say credentials are stored and refreshed automatically. On a post-login `401`, Claude Code refreshes, reconnects, and retries once, then flags failure in `/mcp`; a rejected refresh token prompts re-authentication. `claude mcp logout <name>` clears stored credentials. [Claude MCP guide](https://code.claude.com/docs/en/mcp) |

**Version-sensitive checks.** The Codex guide calls the stable shared CIMD document `https://chatgpt.com/oauth/codex/client.json` “coming soon,” while the pinned 0.155.1 source selects it for issuer-bound callbacks. In this run, Codex selected that path and the document was live. The per-server CIMD path is `https://chatgpt.com/oauth/codex/<callback_id>/client.json`. [Codex guide](https://developers.openai.com/codex/mcp), [0.155.1 registration source](https://github.com/openai/codex/blob/rust-v0.155.1/codex-rs/rmcp-client/src/oauth_client_registration.rs). Claude Code 2.1.277 release notes report a fix for reusing a registration with a different redirect and for registration persistence races; 2.1.280 reports a reconnect fix after remove/re-add under the same name. These are release claims, not proof for ADI-177. [2.1.277 release](https://github.com/anthropics/claude-code/releases/tag/v2.1.277), [2.1.280 release](https://github.com/anthropics/claude-code/releases/tag/v2.1.280).

The [MCP authorization specification](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization) sets the protocol baseline. The observed matrix is the evidence for these client versions; the source review describes behavior the probe did not exercise, especially failure recovery and issuer validation.
