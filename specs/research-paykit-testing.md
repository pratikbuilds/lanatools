# Pay Kit testing ground for LanaTools

Research snapshot: 2026-09-24. This is a proposed test arrangement, not a report of a running integration.

## Recommendation

Use **a local paywalled merchant backed by Surfpool** as the deterministic payment fixture, then run the actual LanaTools MCP server and two real MCP clients against it. Keep the public pay.sh catalog visible in LanaTools, but give the test environment a separate fixture catalog entry that points only to the fixture merchant. A second, optional test lane can use the hosted Surfpool sandbox and a publicly reachable sandbox merchant. Neither lane should send sandbox payment proofs to production catalog URLs. The public registry's `service_url` is a production HTTPS URL; only entries with an optional `sandbox_service_url` advertise a staging merchant, and those merchants must point to the Surfpool sandbox RPC. [pay-skills contributing guide](https://github.com/solana-foundation/pay-skills/blob/main/CONTRIBUTING.md#optional-frontmatter), [pay.sh catalog guide](https://pay.sh/docs/using-pay/skills).

The first fixture can be the [Pay Kit playground](https://github.com/solana-foundation/pay-kit/blob/main/playground/README.md), which already has charges, x402, subscriptions, and sessions. Its Express API is in [`typescript/examples/playground-api`](https://github.com/solana-foundation/pay-kit/tree/main/typescript/examples/playground-api). This is a merchant fixture, not LanaTools' payment or budget implementation.

## Payment-form test matrix

| Form | Protocol and exposure | Local test |
| --- | --- | --- |
| Fixed | MPP `charge` or x402 `exact`; a fixed amount settles once. | Call one playground paid route through LanaTools, verify the 402 amount against a client's remaining lifetime limit, reserve before payer signing, then check result, receipt, and spent amount. Force each protocol once if the route offers both. |
| Metered | x402 `upto`; a ceiling is authorized, actual usage charged, remainder refunded. | Reserve the **ceiling**, not estimated usage; run zero, partial, and maximum use; keep reservation until verified settlement or refund. |
| Subscription | MPP `subscription`; first call creates a recurring on-chain authorization and later calls can reuse it. | Test activation and reuse locally, but treat a recurring puller as potentially greater than one-call exposure. Do not enable it under a finite client lifetime limit until revocation and total future debit bounds are proven. |
| Session | MPP `session`; deposit a channel cap, sign off-chain vouchers while deliveries stream, settle later when closed. | Reserve the entire cap from open through verified close; test partial delivery and stalled closure. The documented client uses `createSessionFetch` and a payment-channel opener rather than ordinary `createPayKitClient.fetch`. |

Protocol assignments and semantics above come from [Pay Kit payment schemes](https://pay.sh/docs/sdk/typescript/schemes) and [client docs](https://pay.sh/docs/sdk/typescript/client). The reservation rules are LanaTools design consequences of its own cumulative client limit, not behavior supplied by Pay Kit.

## Integration sequence

LanaTools currently has only a health route; its API and web dev servers use ports 3000 and 5173. The Pay Kit playground documents the same ports, so a simultaneous local run needs distinct ports. Also, LanaTools' current Cloudflare site Preview forwards `/api` to the production API. It cannot serve as the closed test environment without separate API bindings and state. These are observations from the current LanaTools checkout, not Pay Kit behavior.

1. Run the playground/API against **one explicit Surfpool RPC** and exercise its routes using the CLI or a throwaway `KeyPairSigner`; capture the challenge, payment proof, settlement receipt, and all network identifiers. This establishes a known merchant baseline. [Playground README](https://github.com/solana-foundation/pay-kit/blob/main/playground/README.md), [TypeScript README](https://github.com/solana-foundation/pay-kit/blob/main/typescript/README.md).
2. Point LanaTools' development catalog fixture at those local merchant routes. Run the hosted MCP implementation locally, connecting two genuine OAuth clients. The fixture must go through the **same** catalog validation, grant, budget reservation, Pay Kit, and activity path as a production call. Keep the fixture catalog separate so `localhost` cannot leak into the public provider catalog. The public catalog requires HTTPS production service URLs and valid Solana mainnet payment for paid listings. [pay-skills README](https://github.com/solana-foundation/pay-skills#payment-requirements).
3. Start with fixed charges, then metered usage, sessions, and subscriptions as the signer and reservation semantics are proven. Inject concurrent calls, a changed 402 quote, insufficient balance, a malformed challenge, a lost merchant response after settlement, retry, reconnect, and revocation. Assert that a denied or unresolved payment never produces an additional signature or second charge. These are proposed LanaTools checks from the [agent-payments scope](./agent-payments.md), not Pay Kit's built-in tests.
4. For a shared, remote test, host the fixture merchant over HTTPS, point it and LanaTools at `https://402.surfnet.dev:8899`, and use test wallets only. `sandbox_service_url` can describe a provider's staging endpoint, but public catalog publication is unnecessary for LanaTools' private test fixture. [pay-skills contributing guide](https://github.com/solana-foundation/pay-skills/blob/main/CONTRIBUTING.md#optional-frontmatter), [CLI flags](https://pay.sh/docs/toolchain/global-flags).
5. Only after this closed loop works, make one deliberately capped real paid call to a production catalog provider. Local and Surfpool tests cannot prove that an arbitrary provider supports sandbox payments, that its live challenge matches catalog metadata, or that its response is useful. [Catalog docs](https://pay.sh/docs/using-pay/skills).

## Open technical checks before implementation

### Privy wallet on a local validator

Privy's current Solana SDK separates `signTransaction` (returns signed bytes without broadcast) from `signAndSendTransaction`. Its `@solana/kit` example builds a transaction with a blockhash from a caller-selected RPC, and its signing guide shows submission of signed bytes through that RPC. This supports a local Surfpool proof: fund the test embedded-wallet address on the local validator, build a transaction with that validator's blockhash, request a Privy signature, then broadcast and confirm through `http://localhost:8899`. Privy remains a remote signing service; only construction, broadcast, and settlement are local. [Privy signing](https://docs.privy.io/wallets/using-wallets/solana/sign-a-transaction), [Privy Kit integration](https://docs.privy.io/wallets/using-wallets/solana/kit-integrations).

That documentation does not establish that LanaTools' **server-authorized** Privy signer works with every Pay Kit payer contract on localnet. Prove that exact path with a test wallet and signer policy before relying on it. Prefer sign-only plus LanaTools' Surfpool RPC for this proof; Privy's combined send API introduces a separate broadcast path. [Privy send](https://docs.privy.io/wallets/using-wallets/solana/send-a-transaction).

- **Payer signer seam:** The public Pay Kit client docs show `KeyPairSigner`. They do not demonstrate Privy embedded-wallet signing for `charge`, `upto`, subscription activation, or per-delivery session vouchers. Trace the current TypeScript client source and prove each required signing method with a Privy test wallet before depending on it. [Client docs](https://pay.sh/docs/sdk/typescript/client), [Signer docs](https://pay.sh/docs/sdk/typescript/signers).
- **Pre-signing budget seam:** `client.fetch` hides the 402 → pay → retry loop. LanaTools must inspect the live challenge and atomically reserve exposure before allowing its payer signer to authorize payment. Check whether the SDK exposes a sufficient hook; otherwise wrap at the signer/challenge boundary or use the protocol builder path. A post-`fetch` ledger write is too late. [Client docs](https://pay.sh/docs/sdk/typescript/client), [Pay Kit interface specification](https://github.com/solana-foundation/pay-kit/blob/main/docs/paykit-interface.md).
- **Refund and uncertain-result seam:** A metered or session reservation may outlive the HTTP result. Inspect actual on-chain settlement/receipt behavior and run failure injections before deciding when to release it. [Schemes docs](https://pay.sh/docs/sdk/typescript/schemes), [payment-channels README](https://github.com/solana-foundation/payment-channels/blob/main/README.md).

No live merchant, wallet, or chain test was executed for this note. The `pay-kit` repository could not be cloned in this sandbox because direct shell DNS access to GitHub was unavailable; links above are to the official GitHub pages and pay.sh documentation inspected via web browsing. In particular, this note does **not** claim that payer-side Privy signing already works.
