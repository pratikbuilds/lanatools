# ADI-176 Pay Kit payment from a server-authorized Privy wallet

Status, September 27, 2026: the payer targets the existing `pay --sandbox gate api` merchant configured by `packages/testbed/merchant.yaml`. In the browser, the official Privy signer paid the YAML merchant through both fixed MPP and x402. The Pay Kit limit and Privy policy denial paths also passed.

## Flow

Run `bun run testbed start` to serve the YAML merchant at `http://127.0.0.1:1402/api/v1/fixed`. The spec declares fixed MPP and x402 charges plus an over-limit MPP charge on the hosted Surfpool sandbox. Run `bun --env-file=.env run testbed:paykit` for the payer and `bun run proof` for the local-only sign-in page. The browser sends its Privy token to the payer on `127.0.0.1:1403`; the payer verifies it and creates a disposable user-owned policy and wallet with a server key quorum. The server key is held only in the payer process. The payer uses `@solana/keychain-privy` to sign.

Before paying, the payer reads the YAML merchant's live MPP 402 challenge and checks its amount, token mint, and localnet network. It reserves the quoted maximum from a 0.10 USDC local wallet budget before Pay Kit `client.fetch`. Pay Kit then pays the fixed endpoint over MPP or x402. The payer checks the receipt, confirmed transaction, payer debit, merchant credit, and payer SOL balance before recording the spend. A failed or uncertain payment retains its reservation. The Pay Kit denied mode uses a 0.005 USD cap and requires an `amount_exceeds_limit` rejection. The Privy denied mode uses a 0.02 USD fixture, above the policy's 0.01 USD transfer limit, and requires a structured Privy `policy_violation` with unchanged balances.

## Evidence and limits

- `pay --sandbox curl` paid the YAML merchant and the original testbed check verified its receipt and merchant balance change.
- A Pay Kit keypair client rejected the YAML challenge with `amount_exceeds_limit` under a 0.005 USD cap. With 0.01 USD allowed, it returned HTTP 200 and an MPP receipt from the same gateway.
- The browser x402 payment returned HTTP 200 and confirmed signature `4UobsQeNBh3k9HujsNj8voQwZVT65cLiao8FJzz3GqtXejkYzEw6AyqsLKiiNed9299qLPs6CW1hYfjZnZeR11yw`. The Privy wallet fell from 100000 to 90000 atomic USDC while the merchant rose from 1000030000 to 1000040000. The browser MPP payment then confirmed signature `3rZkCqtSZyc7VaV63z7AueqEZMbqvr4RoBrbN9JYq43swF8cvf4o9hE5XR81ZrRKDLNKPtqDX13KewAqc1RUHKft`, with wallet 90000 to 80000 and merchant 1000040000 to 1000050000. The wallet paid no SOL network fee.
- The Pay Kit limit rejected 0.01 USDC before signing under a 0.005 USD cap. The Privy policy returned `policy_violation` for the 0.02 USDC fixture. Both denial paths left wallet and merchant balances unchanged.
- The local pay.sh gateway puts a raw Solana signature in the x402 `payment-response` header. Pay Kit's standard x402 receipt decoder expects base64 JSON, catches its decode error, and omits the `paid` progress event. The proof accepts this local gateway header as a signature and verifies it through Surfpool before recording settlement. A standards-compliant external x402 endpoint should use Pay Kit's `paid` event; that route has not been exercised here.
- `createPayKitClient` currently types its signer as `KeyPairSigner`, while `@solana/keychain-privy` supplies a remote signer without a local `keyPair`. The proof uses a type cast at this seam. Both fixed protocols worked at runtime, but this is an upstream Pay Kit typing gap; the proof does not modify Pay Kit.
- The prior Privy MPP and x402 signatures (`2Ar9cbWYsaSTiTNhT1NzaUhjNicKmXmDhxtzcfqd2ybQZZS8tA2zyCLqHpmKrtgaMvXXp9QMq5tAbdHmcFg9aApN`, `VXkf2w1H45R65vZVA1nZCaKC8hSG2jskiZzkmirhZ3FtGqmy7iWrF5Q722NQKaC6UH4nUjzec4qRqk3D8qWqoBx`, and `4sB4LtyYNnADrEvjiNNSk7YqNEBoxXf7FEmxye4fp8VLg2o2ubu14NDfdGx1HUpdd7tMmMV7gckKcUs8A7qAW1ks`) came from a separate local Pay Kit merchant on Surfpool, not from the YAML gateway. They establish the signer seam for those protocols but do not establish the current end-to-end flow.
- This is sandbox settlement. The in-memory reservation limit applies to one payer process, not across restarts or server instances. Production catalog calls need a durable atomic wallet and per-client reservation store, quote-specific ceilings, settlement reconciliation, and funding on the challenged network. Privy evaluates Solana instructions separately, so its 0.01 USDC transfer rule does not enforce a cumulative transaction or wallet cap by itself.
- A temporary server-owned policy passed a standalone create/delete check, and the user reported that the payment flow worked with it. On Ctrl-C, Privy archived the wallet but refused to delete the policy and key quorum because both still had an associated wallet signer. The server-owned policy did not solve cleanup, so the proof returned to user-owned policies. Earlier user-owned-policy deletion also failed with `Invalid JWT token provided`.
- The signer must be detached before archiving the wallet to release the policy and quorum. The archived wallet returned `Wallet not found` to an attempted signer removal. Detaching an active user-owned wallet requires an authorized Privy update; that step is not yet implemented or verified in this testbed.
- The strict Privy policy allows only bounded `TransferChecked` payments plus Compute Budget and Memo instructions. Payment-channel schemes (`x402-upto` and `mpp-session`) are deferred; this YAML and browser proof expose neither route. Their future implementation needs a bounded channel-open policy and an available session client.

## Reproduce

Use a dedicated Privy development app. Put `PRIVY_APP_ID` and `PRIVY_APP_SECRET` in the ignored root `.env`, and `VITE_PRIVY_APP_ID` in `apps/proof/.env.local`. Restart `bun run testbed start` so the gateway loads the revised YAML, then restart `bun --env-file=.env run testbed:paykit` and run `bun run proof`. Sign in at `http://localhost:5174` and use **Pay with MPP**, **Pay with x402**, **Try denied payment**, and **Try Privy policy denial**. Ctrl-C on the payer archives wallets and attempts to delete their policies and key quorum; check the process log for cleanup results.

## Devnet

Status, September 29, 2026: the YAML merchant runs on devnet with no catalog. Each testbed script takes `--network sandbox|devnet` (sandbox by default), and `packages/testbed/src/networks.ts` holds every per-network difference. `bun run testbed:devnet start` writes `merchant.yaml` with `operator.network: devnet` into `packages/testbed/.state/devnet/` and serves it at the same `http://127.0.0.1:1402` routes with `pay gate api --rpc-url https://api.devnet.solana.com`. Payments go to the default Solana CLI wallet (`solana address`). On its first start, pay creates a gateway fee payer and refuses to run until that wallet holds SOL; the testbed sends it 0.1 devnet SOL from the CLI wallet and restarts. The devnet state persists, so the funded fee payer survives restarts. The sandbox state is still reset on each start.

The live challenge names `network: devnet`, Circle's devnet USDC `4zMMC9srt5Ri5X14GAgXhaHii3GnPAEERYPJgZJDncDU`, the CLI wallet as recipient, and the gateway as fee payer. x402 advertises `solana:EtWTRABZaYq6iMfeYKouRu166VU2xqa1`. Pay Kit 0.12 resolves the same mint for devnet. `bun run testbed:devnet check` pays the fixed route over MPP and x402 with Pay Kit from a new keypair funded by the CLI wallet, then checks the merchant's balance change per transaction. It passed with MPP `5Dxj4TwEhcbm9xMV1jRDaqsebp7DAeygyhSwJLxL26ARGw37wELy1kpHfNbVMX8Xb93s5eWYUDXDiFNo9PdY9Srx` and x402 `338c3jYji5oUbnmDja8SRwDgKJafTiZmxfahAPHAdnbioSyXsn4geWMXbTN863MSYXfwAW5c42vyyEq66oiTCf45`. The same check passed on the sandbox.

`bun --env-file=.env run testbed:paykit:devnet` runs the Privy payer against the devnet merchant, funding each new proof wallet with 0.10 devnet USDC from the CLI wallet through `spl-token transfer`. In a browser run, Privy wallet `R624zEXkLb46eKP7ZyaoyfZBMakp3b8dwFT4gQgJZTG` paid two fixed charges and fell from 0.10 to 0.08 USDC. One run's post-payment balance read then failed with the public RPC's `Too many requests`; the payment had settled and its reservation stayed held. RPC reads now retry rate-limited calls with backoff, and `DEVNET_RPC_URL` selects another devnet RPC. Archived proof wallets keep unspent devnet USDC.

The browser proof also needs `http://localhost:5174` among the Privy app's allowed domains. Without it, Privy returns `invalid_origin` ("Origin not allowed") and its iframe's `frame-ancestors` blocks the page.

`pay` 0.28 cannot pay the devnet merchant: `pay curl` rejects the challenge with "does not have enough balance on `devnet`" even when its wallet holds devnet USDC, with or without `PAY_RPC_URL`. The CLI has no devnet network flag (`--sandbox` and `--local` both select Surfpool). `testbed pay` therefore stays sandbox-only, and `check` pays through Pay Kit on both networks. The public devnet airdrop returned HTTP 429, so funding comes from the CLI wallet rather than the faucet.
